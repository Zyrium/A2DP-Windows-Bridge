# Додавання підтримки мікросхем

BlueCaster керує Bluetooth-адаптером напряму (WinUSB), тому має робити те саме, що й драйвер виробника для Windows, щоб адаптер запрацював; для багатьох мікросхем це означає завантажувати мікропрограму під час кожного запуску. Адаптери Realtek, Intel, Broadcom і CSR уже працюють, як і MediaTek MT7925, MT7927, MT7922, MT7921, MT7902 і MT7663 та Qualcomm QCA61x4, QCA9377, WCN6855, WCN785x і AR30xx (MT7927, MT7922, MT7902, MT7663 і мікросхеми Qualcomm ще не перевірено на обладнанні). Інші мікросхеми MediaTek (старіші) і Qualcomm (QCA6290) поки не працюють, бо для них ще ніхто не написав завантажувача. Для іншої мікросхеми MediaTek почніть із завантажувача MT79xx у `app/src/crates/bt-host/src/mediatek.rs`.

На цій сторінці пояснено, як додати завантажувач. Для цього потрібен адаптер із відповідною мікросхемою, а в супровідників такого немає. Навіть якщо ви не пишете код, ви можете допомогти: кроки 1 і 2 дають звіт, потрібний розробникові.

{: .note }
Задум, що лежить в основі, і відкриті питання описано в [нотатці для розробників](../chip-bringup-dev).

## Що вам потрібно

- Адаптер, під'єднаний до ПК з Windows 10 / 11
- BlueCaster 2.0.2 або новіший (для кроків нижче достатньо самої програми)
- Щоб написати завантажувач: середовище збирання, як описано в розділі [Збирання](building), а також [USBPcap](https://desowin.org/usbpcap/) з [Wireshark](https://www.wireshark.org/), щоб записати, що робить власний драйвер Windows

## Крок 1: Передайте адаптер BlueCaster

1. **Параметри > Режим розробника**: увімкнено
2. **Адаптери**: на картці адаптера натисніть **Замінити драйвером WinUSB** (Windows попросить дозвіл адміністратора). Для мікросхеми, яку BlueCaster ще не може використовувати, ця кнопка доступна лише в режимі розробника
3. Якщо на картці написано **Під'єднайте знову або перезавантажте Windows**, зробіть це

Поки адаптер працює з WinUSB, власний Bluetooth Windows не може ним користуватися. Якщо на ноутбуці ця мікросхема — єдиний Bluetooth, клавіатури, миші й гарнітури, підключені через Windows, перестануть працювати, доки ви не повернете драйвер кнопкою **Відновити початковий драйвер** на тій самій картці.

## Крок 2: Зчитайте, що повідомляє мікросхема (опитування мікросхеми)

У розділі **Мікропрограма** на картці адаптера натисніть **Зчитати дані мікросхеми**. Стек Bluetooth ненадовго зупиняється, виконується опитування, і Провідник відкриває звіт `probe-<date>_<time>.json` у `logs\probe\` у папці параметрів (`%APPDATA%\BlueCaster`). Зберігаються 10 найновіших звітів.

Опитування лише читає дані: воно не надсилає ні HCI Reset, ні команд виробника:

| Запит | Що він показує |
|:--|:--|
| Read Local Version Information | Версія HCI / LMP, виробник (company ID), LMP subversion: часто це версія ПЗП або мікропрограми |
| Read BD_ADDR | Адреса адаптера (на деяких мікросхемах — нуль або заповнювач, доки не запущено мікропрограму) |
| Read Local Supported Commands / Features, Read Buffer Size | Що пропонує запущений код: ПЗП часто пропонує набагато менше, ніж мікропрограма |
| Read Local Name | Деякі ПЗП називають себе |
| LE Read Local Supported Features, LE Read Buffer Size | Те саме для LE |
| Дескриптор USB-пристрою, рядки виробника й продукту | Стандартні запити USB через канал за замовчуванням |

Крім того, опитування записує конфігурацію USB, яку повідомляє Windows (інтерфейси, кінцеві точки), і кожну подію, яку мікросхема надіслала без запиту. Запит без відповіді теж записується: мікросхема, яка нічого не відповідає, доки не завантажено мікропрограму, — це вже знахідка.

З командного рядка — із VID:PID або ідентифікатором екземпляра адаптера (їх показує картка адаптера):

```bat
"%LOCALAPPDATA%\BlueCaster\bluecaster-core.exe" --cli -u 0e8d:7961 --probe
```

Спершу закрийте BlueCaster з області сповіщень, бо адаптером одночасно може користуватися лише одна програма.

**Надсилання звіту**: після **Зчитати дані мікросхеми** картка адаптера показує зчитані дані й кнопку **Повідомити на GitHub**. Кнопка відкриває новий issue, у якому вже заповнено версію, адаптер, цей підсумок, збірку Windows і сам звіт. Вкажіть, звідки адаптер (для вбудованого адаптера — модель ноутбука).

Якщо звіт задовгий для issue, поле **Probe report** залишається порожнім, а Провідник показує файл звіту. Перетягніть файл у це поле: без нього GitHub не створить issue. Звіти зберігаються в `%APPDATA%\BlueCaster\logs\probe`; найновіший має найпізнішу дату в назві. Звіт містить Bluetooth-адресу й назву адаптера, але нічого про ваші навушники. **Пакет діагностики** (екран «Діагностика») із записами HCI також містить звіти опитування в папці `probe/`.

## Крок 3: Запишіть, що робить драйвер Windows

Опитування показує стан мікросхеми, але не те, як його змінити. Це знає драйвер виробника для Windows: запишіть його роботу один раз, і завантажувач зможе повторити ті самі кроки.

1. **Відновити початковий драйвер** на картці адаптера, щоб адаптером знову керував драйвер Windows
2. Установіть USBPcap і Wireshark; запустіть Wireshark від імені адміністратора й записуйте той інтерфейс USBPcap, до якого під'єднано адаптер. `USBPcapCMD.exe` (у папці USBPcap) показує пристрої на кожному кореневому концентраторі; вбудований адаптер ноутбука під'єднано до внутрішнього концентратора, і часто він відображається лише як «USB Composite Device» або за своїм VID:PID. Якщо не впевнені, записуйте всі інтерфейси USBPcap одночасно
3. Змусьте драйвер завантажити мікропрограму: від'єднайте й знову під'єднайте адаптер, а для вбудованого виберіть **Вимкнути пристрій** і **Увімкнути пристрій** у Диспетчері пристроїв. Мікропрограма, що зберігається після теплого перезапуску, може завантажитися лише після повного вимкнення ПК
4. Зупиніть запис, щойно адаптер з'явиться в параметрах Bluetooth Windows. Знайдіть серед перших пакетів дескриптор пристрою адаптера (з його VID:PID), відфільтруйте записи за його адресою (`usb.bus_id == <bus> && usb.device_address == <address>`) і збережіть запис

На що звертати увагу (по черзі):

- **Керувальні передавання** перед будь-якою командою HCI: `bmRequestType` 0x40 / 0xC0 (vendor, OUT / IN) з їхніми `bRequest`, `wValue`, `wIndex`. Вони часто зчитують ідентифікатор мікросхеми або скидають частину мікросхеми
- **Команди HCI** (запити класу, `bmRequestType` 0x20) з кодами операцій від 0xFC00 до 0xFFFF: команди виробника. Довга серія команд з одним кодом операції й великими параметрами — це передавання мікропрограми; відповіді на неї показують, як підтверджується кожна частина
- **Події**, що не є Command Complete / Status: події виробника (код 0xFF або власний код виробника, як-от 0xE4), наприклад «мікропрограму запущено» або підтвердження кожної частини мікропрограми замість Command Complete
- Дані **Bulk OUT** перед першим HCI Reset: деякі мікросхеми приймають мікропрограму через канал ACL
- Звідки береться файл: порівняйте надіслані дані з файлами в папці драйвера (Диспетчер пристроїв > відомості про драйвер або `C:\Windows\System32\DriverStore\FileRepository\`) і з файлами мікросхеми в [linux-firmware](https://git.kernel.org/pub/scm/linux/kernel/git/firmware/linux-firmware.git/tree/) (`mediatek/`, `qca/`), які можна поширювати й які користувачі BlueCaster можуть завантажити

Занотуйте кожну паузу, яку драйвер робить між кроками (див. позначки часу в записі): мікросхема, яка ще скидається, не відповідає.

{: .warning }
Працюйте із записами, звітами опитування й документацією виробника. Не копіюйте й не відтворюйте близько до тексту GPL-код, наприклад драйвери ядра Linux `btmtk` чи `btqca`: BlueCaster ліцензовано за Apache-2.0 або MIT, і похідний від них завантажувач не можна було б включити.

## Спробуйте без збирання: скрипти мікросхеми {#chip-scripts}

Перш ніж писати завантажувач, спробуйте записану послідовність на адаптері за допомогою **скрипту мікросхеми**: це та сама послідовність у вигляді тексту, по одному запиту на рядок, яка виконується замість стеку Bluetooth. Той, хто не має адаптера, може написати скрипт і надіслати його власникові адаптера; результат повертається у вигляді звіту, без нової збірки.

**Як запустити**: у режимі розробника відкрийте **Розробник > Мікросхема**, виберіть адаптер (з WinUSB), введіть скрипт або відкрийте файл і натисніть **Виконати**. Відповідь на кожен рядок з'являється нижче, а **Показати звіт** відкриває `script-<date>_<time>.json` у `logs\probe\` (скрипт теж міститься у звіті). З командного рядка: `bluecaster-core --cli -u <adapter> --script <file>`.

```text
# один запит на рядок; числа шістнадцяткові (0x необов'язково), крім wait, timeout= і chunk=
hci 1001                           # команда HCI: код операції, потім байти параметрів
hci fc05 ff
bulk fc09 00 01 02                 # те саме через канал bulk OUT
usb in vendor device 63 0 0 4      # control IN: тип, отримувач, запит, значення, індекс, довжина
usb out vendor device 64 0 0 01    # control OUT: ..., потім байти даних
wait 100                           # мілісекунди
expect e4 02 01 timeout=5000       # подія: її код і перші байти параметрів
bootloader off                     # режим завантажувача (увімкнено від початку)
upload mediatek/patch.bin fc6f 01 01 chunk=240 ack=event:e4:02,01
upload-bulk patch.bin fc09 01      # те саме через канал bulk OUT
```

- `hci` і `bulk` чекають на Command Complete або Command Status команди (2 s) і записують відповідь незалежно від її статусу
- `upload` надсилає файл із папки мікропрограм командами з цим кодом операції — кожна з байтами заголовка й до `chunk` байтів файлу (за замовчуванням 240) — і чекає на кожне підтвердження: `ack=complete` (за замовчуванням: Command Complete або Command Status цього коду операції зі статусом 0) або `ack=event:<code>[:<bytes>]`. Статус помилки зупиняє завантаження
- Скрипт зупиняється на першому рядку, що не виконався (немає відповіді, помилка, відсутній файл), і вказує, на якому саме
- Події, які не відповідають жодному рядку, теж зберігаються у звіті

**Безпека**: без запиту виконуються лише запити, про які відомо, що вони тільки читають: стандартні запити читання HCI (інформаційні параметри й параметри стану, Read Local Name, запити читання LE), стандартні запити дескрипторів USB, `wait`, `expect` і `bootloader`. Скрипт із будь-яким іншим рядком виконується, лише якщо ви це дозволите (**Виконати їх** під списком таких рядків; `--allow-writes` у командному рядку). Команди виробника, які можуть записувати в пам'ять, що зберігається в мікросхемі після вимкнення живлення, не виконуються ніколи, хоч би що ви дозволили (`denied_opcodes` в `app/src/crates/bt-host/src/chips.rs`: поки що це BCCMD від CSR). Режим завантажувача ввімкнено від початку, тож закриття адаптера після скрипту не надсилає HCI Reset. Мікропрограма, завантажена в RAM мікросхеми, зникає після повторного під'єднання.

## Крок 4: Напишіть завантажувач

Далі шляхи вказано відносно кореня репозиторію. Важливі три крейти:

| Крейт (пакет) | Папка | Що там |
|:--|:--|:--|
| `bt-host` | `app/src/crates/bt-host` | Bluetooth-хост: завантажувачі, опитування, визначення мікросхеми |
| `bluecaster-core` (бібліотека) | `app/src/crates/core` | Параметри й адаптери: який завантажувач запускається |
| `bluecaster-core-exe` | `app/src/core` | Виконуваний файл служби (`bluecaster-core.exe`): запити вікна, примітки до адаптерів |

Обидва останні мають у назві «core»; `cargo -p` приймає наведені вище назви пакетів.

Завантажувач — це скінченний автомат без власного введення-виведення: він отримує події контролера, результати своїх запитів USB і свій таймер, а повертає **дії**, які виконує програма. Тому завантажувач можна тестувати без мікросхеми, а подробиці USB і потоків лишаються поза ним.

1. Скопіюйте `app/src/crates/bt-host/src/bringup/sample.rs`, повний завантажувач для вигаданої мікросхеми разом із тестами, у `app/src/crates/bt-host/src/<vendor>.rs` (наприклад, `mediatek.rs`). Додайте `pub mod <vendor>;` до `app/src/crates/bt-host/src/lib.rs`, в алфавітному порядку серед інших модулів
2. Збережіть назви: тип — `Loader` (використовується як `<vendor>::Loader`), `vendor()` повертає назву виробника. Залиште тести у файлі, як у прикладі
3. Замініть усе, що в прикладі позначено як «made up», тим, що показали кроки 2 і 3: перевірку версії, запит USB, назву файлу, команду завантаження й спосіб її підтвердження, запуск мікропрограми
4. Перепишіть коментар модуля на початку: що потрібно мікросхемі, кроки по черзі й звідки взято кожен факт (ваш запис роботи драйвера Windows, документація виробника, звіти опитування). Не посилайтеся на вихідний код інших драйверів як на джерело кроку

### Інтерфейс

Усе міститься в `app/src/crates/bt-host/src/bringup.rs`.

| Метод `ChipLoader` | Викликається |
|:--|:--|
| `vendor()` | Для рядків журналу («MediaTek») |
| `start()` | Один раз, на відкритому адаптері, перед ініціалізацією HCI |
| `on_event(event)` | Для кожної події HCI: код, довжина, параметри |
| `on_control(result)` | З результатом останнього `UsbControl`: зчитані байти або причина невдачі |
| `on_timeout()` | Коли спрацьовує таймер останнього `Timer` |
| `missing_file_hint(file)` | Для журналу, коли завантажувач завершився з `MissingFile`: що й куди покласти («x.bin from linux-firmware (mediatek/)») |
| `step()`, `progress()` | Після кожного пакета дій: назва кроку («download») і його поступ (надіслано команд із загальної кількості) — для екрана «Адаптери», поки адаптер запускається |

Після `Done` програма відкидає завантажувач, і запізніла відповідь до нього вже не доходить.

| `Action` | Що робить |
|:--|:--|
| `Command(bytes)` | Надсилає команду HCI (код операції, довжина, параметри) через керувальний канал; записується в запис HCI |
| `BulkCommand(bytes)` | Надсилає команду (ті самі байти, що й для `Command`) через канал bulk OUT, через який деякі завантажувачі приймають мікропрограму |
| `UsbControl(request)` | Керувальне передавання через канал за замовчуванням (регістри виробника); виконується одразу, і `on_control` отримує результат перед наступною дією. У запис HCI потрапляє як примітка |
| `Bootloader(on)` | Для мікросхеми, завантажувач якої відповідає через канал bulk IN або якій не можна надсилати HCI Reset (деякі від нього зависають); див. «Шаблони». Мікросхемі з ПЗП, яка нормально відповідає на HCI, це не потрібно |
| `Timer(ms)` | Запускає або перезапускає єдиний таймер завантажувача |
| `Done(Ok(outcome))` | Готово: далі йде ініціалізація HCI. `AlreadyRunning`, `Loaded { firmware, detail }`, `Rom` (`Probed` належить опитуванню) |
| `Done(Err(error))` | Адаптер неможливо використовувати: `MissingFile(name)`, `BadFile { file, why }`, `Command { opcode, status }`, `Timeout(step)`, `Rejected(code)`, `BadVersion`, `UnsupportedVariant(v)`, `Unsupported(why)`, `Host(why)` |

Допоміжні функції, щоб завантажувачу не доводилося розбирати байти вручну:

- `hci_command(opcode, params)` створює команду
- `parse_event(event)` повертає `HciEvent::Complete { opcode, status, ret }` (параметри повернення після статусу), `Status { opcode, status }`, `Vendor(params)` (подія 0xFF) або `Other { code, params }` (будь-який інший код, зокрема власний код виробника, як-от 0xE4)

**Файли мікропрограми**: завантажувач отримує `FileReader` і запитує в нього файл за **назвою без папки** (`"BT_RAM_CODE_MT7961_1_2_hdr.bin"`). Програма шукає файл у папці мікропрограм (`%APPDATA%\BlueCaster\firmware`) і в підпапці виробника в ній (`firmware\mediatek\`), як у linux-firmware; цю підпапку задає крок 6.

### Шаблони

Приклад показує кожен із них; відкиньте те, що не потрібно вашій мікросхемі.

- **Одна команда — одне підтвердження**: надішліть команду, запустіть таймер і в стані очікування приймайте лише підтвердження цього коду операції: Command Complete або, для команди, результат якої надходить пізніше, Command Status зі статусом 0. Усе інше ігноруйте, щоб запізніла відповідь не просунула завантажувач далі
- **Підтвердження подією виробника**: деякі мікросхеми відповідають на кожну частину мікропрограми власною подією замість Command Complete. Чекайте лише на цю подію (її код і параметри, що її ідентифікують); у цьому стані ігноруйте Command Complete або Command Status зі статусом 0 для цієї команди, але все одно завершуйте роботу, якщо будь-який із них містить статус помилки. Приклад вважає Command Complete і Command Status тим самим підтвердженням, тож для цього його `on_event` потребує `match` і за станом, і за подією
- **Кілька файлів** (патч, потім конфігурація): завантажте й перевірте всі файли, перш ніж щось надсилати, надсилайте їх по черзі й укажіть останній у `Loaded { firmware, .. }` (інші названо в рядках журналу)
- **Навмисна пауза** (драйвер чекає 100 ms перед наступним кроком): додайте для неї окремий стан і надішліть `Timer(100)`; у цьому стані `on_timeout` надсилає наступний крок, а не завершується невдачею. У тестах `SimRun::timeouts` рахує й такі паузи
- **Команда з двома відповідями** (підтвердження, а потім подія виробника, як-от «мікропрограму запущено»): два стани, другий — із власним таймером. Так влаштовано `Launching` і `Starting` у прикладі. Якщо подія містить код результату, поганий код завершує завантажувач із `Rejected(code)`
- **Статус помилки** в Command Complete чи Command Status завершує завантажувач із `Command { opcode, status }`
- **Режим завантажувача**: `Bootloader(true)` перед першою командою, ще до перевірки версії. У разі успіху (`Loaded`, а також `AlreadyRunning`) надішліть `Bootloader(false)` безпосередньо перед `Done`, щоб ініціалізація HCI працювала як звичайно; після невдачі залиште режим увімкненим, бо мікросхема ще в завантажувачі. Саме це робить `finish()` у прикладі
- **Уже працює**: якщо версія або регістр показують робочу мікропрограму, одразу завершуйте з `AlreadyRunning`. Адаптер зберігає мікропрограму, доки не втратить живлення, і повторне завантаження може не вдатися
- **Спершу перевірте файл**: розберіть і перевірте весь файл, перш ніж надсилати будь-яку його частину (`BadFile` із причиною), і вказуйте точну назву відсутнього файлу
- **Лише ваша мікросхема**: якщо завантажувач охоплює лише деякі мікросхеми виробника, перед надсиланням будь-чого перевірте, що адаптер — одна з них (за регістром ідентифікатора мікросхеми або за ідентифікаторами USB через `ControlRequest::device_descriptor()`); інакше завершуйте з `Unsupported`
- **Записуйте в журнал** на рівні `info` те, що дізнаєтеся від мікросхеми (ідентифікатор мікросхеми, версія ПЗП, вибраний файл): саме ці рядки видно у звітах
- Ніколи не записуйте у флеш-пам'ять або OTP-пам'ять мікросхеми й читайте файли лише через `FileReader`

## Крок 5: Перевірте його на симульованому контролері

Тести використовують `app/src/crates/bt-host/src/bringup/sim.rs`. Ви пишете невелику симульовану мікросхему (`impl SimController`), яка відповідає на команди й керувальні передавання так само, як справжня у вашому записі, а `sim::run(&mut loader, &mut chip)` керує завантажувачем точно так, як програма, разом із таймером. Результат (`SimRun`) містить підсумок, кожну надіслану команду з її каналом (`commands[i].bulk`), кожне керувальне передавання, стан режиму завантажувача наприкінці (`bootloader`) і кількість спрацювань таймера. `sim::command_complete`, `command_status`, `vendor_event`, `event` (будь-який код), `opcode` і `params` створюють і розбирають байти; на команди bulk відповідайте в `bulk_command`.

Як і в прикладі, охопіть щонайменше:

- повне завантаження з перевіркою надісланих команд (кількість, порядок, розміри, канал)
- режим завантажувача наприкінці кожного випадку, якщо завантажувач його використовує
- уже запущену мікропрограму
- відсутній файл і пошкоджений файл (з якого нічого не надіслано)
- відхилену команду (статус помилки), мовчазний контролер (тайм-аут) і кожне очікування, яке може завершитися тайм-аутом
- невдале передавання USB, якщо завантажувач його використовує

Байти, скопійовані з вашого запису, — найкращі тестові дані. Запустіть тести так:

```bat
cargo test -p bt-host
```

## Крок 6: Підключіть його до програми

Нижче наведено всі файли, які треба змінити, — для виробника, уже позначеного як непідтримуваний (MediaTek, Qualcomm), або для нового. Для нового виробника компілятор сам укаже на вирази `match`, яким потрібен його варіант; усе інше, зокрема всі зміни для вже позначеного виробника, допоможе знайти лише цей список.

**Одна мікросхема чи весь виробник?** Завантажувач зазвичай охоплює лише деякі мікросхеми виробника (MT7921, але не MT7925). Тоді статус «непідтримуваний» можна зняти лише з цих мікросхем: внесіть їхні VID:PID до `LOADER_CHIPS` в `app/src/crates/bt-host/src/chips.rs` і залиште виробника в `listed_chips_only()`. Після цього `chips::chip_supported(vendor, vid, pid)` і `chip_support_tag()` відповідають для кожного адаптера окремо, і від них залежать позначка в назві адаптера, його примітка на екрані «Адаптери», чи пропонує цей екран WinUSB, і попередження «not implemented». Вилучайте виробника з `listed_chips_only()` лише тоді, коли завантажувач охоплює всі його мікросхеми (як у Intel).

{: .note }
Зберігайте закінчення рядків кожного файлу: одні вихідні файли використовують CRLF, інші — LF. Деякі редактори й `sed -i` у Git Bash непомітно їх змінюють, а `cargo fmt` не відновлює. Це видно з `git diff --stat`: у файлі, який ви змінили в кількох місцях, змінено кожен рядок. У такому разі перед комітом поверніть файлу попередні закінчення рядків (наприклад, перемикачем закінчень рядків у рядку стану VS Code).

**Визначення** (`app/src/crates/bt-host/src/chips.rs`):

1. `ChipVendor`: новий виробник отримує варіант (з рядком документації) і гілку в `name()`. Для будь-якого виробника оновіть коментар документації переліку (які виробники мають завантажувачі) і рядок документації варіанта («not supported»)
2. Деякі мікросхеми: їхні VID:PID у `LOADER_CHIPS` і тест у модулі завантажувача, який перевіряє, що його власна перевірка мікросхеми (ідентифікатор мікросхеми, версія) приймає саме ці записи. Увесь виробник: вилучіть його з `listed_chips_only()`
3. `vendor_for_usb()`: USB VID виробника. VID, який використовують і інші виробники, потрібно зіставляти як `VID if pid == PID`, а не цілком: це модулі для ноутбуків під VID виробника модуля (AzureWave 0x13D3, Foxconn 0x0489) і спільні VID, як-от pid.codes 0x1209. Кожен VID із цього списку також змушує `is_bluetooth_vendor_vid` вважати пристрої цього виробника Bluetooth-адаптерами. VID:PID із таблиці Realtek у BTstack або з `OEM_TABLE` (обидві в `resolve_realtek_pid` цього файлу) вважається Realtek ще до звернення до `vendor_for_usb`: перевірте, що вашого немає в жодній із них
4. `company_name()`: company ID від Bluetooth SIG із Read Local Version, якщо його там ще немає
5. Тести: `app/src/crates/bt-host/tests/chips.rs` (VID:PID і позначка)

**Відкриття адаптера**: пристрої класу Bluetooth (клас E0/01/01) відкриваються без змін. Мікросхемі, яка в режимі ПЗП повідомляє клас виробника (FF), також потрібно внести свої VID:PID до `BUILTIN_VENDOR_CLASS` в `app/src/crates/core/src/adapter.rs`; клас видно в рядку `usb.interfaces` звіту опитування.

**Запуск завантажувача** — так само, як для Intel (шукайте `intel_loader`):

6. `app/src/crates/bt-host/src/lib.rs`: поле `HostConfig` на зразок `intel_loader` (зі значенням за замовчуванням у `HostConfig::new`, деструктуруванням у `BtHost::launch` і рядком налагодження) і гілка в `BtHost::launch`, яка встановлює транспорт і замість `setup_hci_and_power_on` викликає функцію запуску з програми, але лише якщо не використовується H4 (`&& !tcp`, як для Intel: контролер емулятора — не справжня мікросхема). За один запуск працює лише один завантажувач: якщо задано прапорці двох виробників (обидва адаптери з WinUSB), перемагає перша гілка, тож тестуйте, коли WinUSB має лише ваш адаптер
7. `app/src/crates/bt-host/src/app.rs`: `start_<vendor>_loader` на зразок `start_intel_loader` (з `use crate::<vendor>;`), який передає завантажувачу `read_firmware_file(&dir, "<vendor>", name)` (назва підпапки — як у linux-firmware) і викликає `start_loader`
8. `app/src/crates/core/src/adapter.rs`, `configure()`: установлюйте поле, коли адаптер цього виробника, для якого `chips::chip_supported(a.vendor, a.device.vid, a.device.pid)` повертає true, має WinUSB і не використовується (як `config.intel_loader`, з повідомленням журналу Intel «in use by another program» для інших), і додайте поле до рядка налагодження `adapter:` там само. Попередження «firmware loading for this chip is not implemented» нижче вже залежить від `chip_supported`
9. `app/src/crates/core/src/service.rs`, `host_config()`: додайте поле до рядка налагодження

**Що показує вікно**:

10. `app/src/core/src/state.rs`, `vendor_note()`: гілка з новим ключем `firmware.vendor_<vendor>`, винесена з гілки `MediaTek | Qualcomm`, і її тест. До цієї гілки функція повертає `firmware.vendor_unsupported` для мікросхем, які відхиляє `chip_supported`, тож інші мікросхеми виробника зберігають цю примітку. Екран «Адаптери» пропонує WinUSB кожному адаптеру, примітка якого не `firmware.vendor_unsupported`
11. `app/lang/*.json` (усі 10 мов, той самий рядок у кожній): новий ключ, як для Intel («Intel adapter. …»). Якщо в ньому згадано кнопку чи папку, використовуйте слова відповідної мови з того самого файлу (кнопка папки мікропрограм — `firmware.open_folder`). Увесь виробник: вилучіть його назву з `firmware.vendor_unsupported`. Деякі мікросхеми: залиште її там, бо інші мікросхеми виробника й далі показують цей текст
12. `app/src/ui/src/lib/links.ts`: сторінка мікропрограм виробника (у `LINKS`, `firmwareUrl()` і `vendorFirmwareUrl()`, як папка Intel у linux-firmware), щоб екран «Адаптери» показував, де взяти файли; тести в `app/src/ui/src/lib/chips.test.ts`. Екран «Адаптери» показує сторінку лише для адаптерів, примітка яких не `firmware.vendor_unsupported`, тож інші мікросхеми виробника її не отримують

**Документація**:

13. Таблиця мікросхем у `docs/setup.md` і `docs/*/setup.md` (усі мови): рядок на зразок рядка Intel, з охопленими мікросхемами, файлами мікропрограми й тим, куди їх класти (папка мікропрограм: `%APPDATA%\BlueCaster\firmware` або її підпапка `<vendor>`; у старіших рядках ще написано «config folder»). Називайте кнопки вікна так, як їх названо у відповідному `app/lang/*.json` (`ui.nav.adapter` для екрана «Адаптери», `firmware.open_folder` для кнопки, що відкриває цю папку). Увесь виробник: вилучіть його з рядка «Not supported». Деякі мікросхеми: залиште виробника там і назвіть мікросхеми, які досі не підтримуються. Додайте виробника до речення на початку розділу про мікропрограму («Intel and Broadcom adapters may need firmware files of their own»)
14. [Перевірене обладнання](hardware) (`docs/hardware.md`), щойно хтось його використає, і вступ до цієї сторінки (`docs/chip-support.md`, усі мови), де названо виробників без завантажувача (деякі мікросхеми: «the other <vendor> chips»)

## Крок 7: Спробуйте на адаптері

Зберіть проєкт у корені репозиторію (`cargo build --release -p bluecaster-core-exe`), закрийте встановлену програму (через її значок в області сповіщень) і запустіть ядро з командного рядка із записом HCI:

```bat
target\release\bluecaster-core.exe --cli -u 0e8d:7961 --scan 5 --hci-capture loader.pklg
```

Журнал показує кожен крок; `loader.pklg` відкривається у Wireshark з усіма командами, подіями й керувальними передаваннями по черзі. Від'єднайте адаптер (або вимкніть ПК) і спробуйте знову: завантаження має працювати на холодній мікросхемі й нічого не робити, якщо мікропрограма вже працює.

{: .note }
Якщо WinUSB мають кілька адаптерів, BlueCaster надає перевагу адаптеру Realtek і застосовує налаштування його мікросхеми, навіть із `-u`. Установіть для **Адаптери > Мікросхема Bluetooth** значення **Не Realtek** або тестуйте, коли WinUSB має лише ваш адаптер.

Потім деякий час передавайте звук на навушники через вікно й перевірте, що адаптер знову працює після **Перезапустити Bluetooth** і після повторного під'єднання. Поки адаптер запускається, екран **Адаптери** показує стан завантажувача під станом Bluetooth («завантаження 42 %» або невдачу); у режимі розробника цей стан лишається видимим і після запуску адаптера — з вашими назвами `step()` і результатом.
