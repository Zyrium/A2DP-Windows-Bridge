# Добавление поддержки чипов

BlueCaster управляет адаптером Bluetooth напрямую (через WinUSB), поэтому сам должен делать то, что обычно делает драйвер производителя для Windows, чтобы адаптер заработал. Для многих чипов это значит загружать прошивку при каждом запуске. Сейчас работают адаптеры Realtek, Intel, Broadcom и CSR, а также MediaTek MT7925, MT7927, MT7922, MT7921, MT7902 и MT7663 и Qualcomm QCA61x4, QCA9377, WCN6855, WCN785x и AR30xx (MT7927, MT7922, MT7902, MT7663 и чипы Qualcomm на реальном оборудовании ещё не проверены). Остальные чипы MediaTek (более старые) и Qualcomm (QCA6290) пока не работают: загрузчик для них ещё никто не написал. Для другого чипа MediaTek начните с загрузчика MT79xx в `app/src/crates/bt-host/src/mediatek.rs`.

На этой странице описано, как добавить такой загрузчик. Вам понадобится адаптер с этим чипом: у сопровождающих такого адаптера нет. Помочь можно и без программирования: по шагам 1 и 2 получается отчёт, который нужен разработчику.

{: .note }
Устройство этого механизма и нерешённые вопросы описаны в [заметке для разработчиков](../chip-bringup-dev).

## Что понадобится

- Адаптер, подключённый к компьютеру с Windows 10 / 11
- BlueCaster 2.0.2 или новее (для шагов ниже достаточно приложения)
- Чтобы написать загрузчик: среда сборки, как описано в разделе [Сборка](building), а также [USBPcap](https://desowin.org/usbpcap/) и [Wireshark](https://www.wireshark.org/), чтобы записать работу драйвера Windows

## Шаг 1. Передайте адаптер BlueCaster

1. Включите **Параметры > Режим разработчика**
2. На экране **Адаптеры** нажмите на карточке адаптера **Заменить на драйвер WinUSB** (Windows запросит права администратора). Для чипа, который BlueCaster пока не поддерживает, эта кнопка доступна только в режиме разработчика
3. Если на карточке появится **Переподключите адаптер или перезагрузите Windows**, сделайте это

Пока у адаптера драйвер WinUSB, Bluetooth Windows не может его использовать. Если другого Bluetooth в ноутбуке нет, клавиатуры, мыши и гарнитуры, подключённые через Windows, перестанут работать. Чтобы вернуть их, восстановите драйвер кнопкой **Восстановить исходный драйвер** на той же карточке.

## Шаг 2. Прочитайте, что сообщает чип (опрос чипа)

В разделе **Прошивка** на карточке адаптера нажмите **Прочитать сведения о чипе**. Стек Bluetooth ненадолго остановится, выполнится опрос, и в проводнике откроется отчёт `probe-<date>_<time>.json` в папке `logs\probe\` внутри папки настроек (`%APPDATA%\BlueCaster`). Хранятся 10 последних отчётов.

Опрос только читает данные. Он не отправляет ни HCI Reset, ни команд производителя:

| Запрос | Что он сообщает |
|:--|:--|
| Read Local Version Information | Версию HCI / LMP, производителя (company ID), LMP subversion: часто это версия ПЗУ или прошивки |
| Read BD_ADDR | Адрес адаптера (у некоторых чипов до запуска прошивки — ноль или заглушка) |
| Read Local Supported Commands / Features, Read Buffer Size | Что предлагает работающий код: ПЗУ часто предлагает намного меньше, чем прошивка |
| Read Local Name | Некоторые ПЗУ сообщают своё имя |
| LE Read Local Supported Features, LE Read Buffer Size | То же для LE |
| Дескриптор USB-устройства, строки производителя и продукта | Стандартные запросы USB через канал по умолчанию |

Кроме того, опрос записывает конфигурацию USB, которую сообщает Windows (интерфейсы, конечные точки), и все события, которые чип отправил сам. Запросы без ответа тоже записываются: если чип молчит до загрузки прошивки, это уже полезный результат.

Из командной строки, с VID:PID или ИД экземпляра адаптера (оба показаны на карточке адаптера):

```bat
"%LOCALAPPDATA%\BlueCaster\bluecaster-core.exe" --cli -u 0e8d:7961 --probe
```

Сначала закройте BlueCaster через значок в области уведомлений: адаптер может использовать только одна программа одновременно.

**Отправка отчёта**: после **Прочитать сведения о чипе** на карточке адаптера появятся прочитанные сведения и кнопка **Сообщить на GitHub**. Кнопка открывает новый issue, где уже указаны версия, адаптер, эта сводка, ваша сборка Windows и сам отчёт. Напишите, откуда у вас адаптер (для встроенного адаптера — модель ноутбука).

Если отчёт слишком длинный для issue, поле **Probe report** останется пустым, а проводник покажет файл отчёта. Перетащите файл в это поле: без него GitHub не создаст issue. Отчёты хранятся в `%APPDATA%\BlueCaster\logs\probe`; самый новый — с самой поздней датой в имени. В отчёте есть адрес Bluetooth и имя адаптера, но нет никаких сведений о ваших наушниках. Отчёты опроса также входят в **Диагностический архив** (экран **Диагностика**) с включёнными записями HCI, в папку `probe/`.

## Шаг 3. Запишите, что делает драйвер Windows

Опрос показывает состояние чипа, но не то, как его изменить. Это знает драйвер производителя для Windows. Запишите его работу один раз, и загрузчик сможет повторить те же шаги.

1. Нажмите **Восстановить исходный драйвер** на карточке адаптера, чтобы адаптером снова управлял драйвер Windows
2. Установите USBPcap и Wireshark. Запустите Wireshark от имени администратора и начните запись на интерфейсе USBPcap, к которому подключён адаптер. `USBPcapCMD.exe` (в папке USBPcap) показывает устройства на каждом корневом концентраторе. Встроенный адаптер ноутбука подключён к внутреннему концентратору и часто виден только как «Составное USB устройство» или по своему VID:PID. Если не уверены, записывайте все интерфейсы USBPcap сразу
3. Заставьте драйвер загрузить прошивку: отключите и снова подключите адаптер, а для встроенного выберите в диспетчере устройств **Отключить устройство** и затем **Включить устройство**. Если прошивка сохраняется при перезагрузке, она может загружаться только после полного выключения компьютера
4. Остановите запись, когда адаптер появится в параметрах Bluetooth Windows. Найдите среди первых пакетов дескриптор устройства адаптера (его VID:PID), отфильтруйте по его адресу (`usb.bus_id == <bus> && usb.device_address == <address>`) и сохраните запись

На что обращать внимание, по порядку:

- **Управляющие передачи** (control transfers) до первой команды HCI: `bmRequestType` 0x40 / 0xC0 (vendor, OUT / IN) с их `bRequest`, `wValue`, `wIndex`. Обычно они читают ИД чипа или сбрасывают часть чипа
- **Команды HCI** (class-запросы, `bmRequestType` 0x20) с кодами операций от 0xFC00 до 0xFFFF: команды производителя. Длинная серия одного и того же кода операции с большими параметрами — это передача прошивки. По ответам видно, как подтверждается каждая часть
- **События**, отличные от Command Complete / Status: события производителя (код 0xFF или собственный код производителя, например 0xE4). Например, «прошивка запущена» или подтверждение каждой части прошивки вместо Command Complete
- Данные **Bulk OUT** до первого HCI Reset: некоторые чипы принимают прошивку через канал ACL
- Откуда берётся файл: сравните отправленные данные с файлами в папке драйвера (диспетчер устройств > сведения о драйвере или `C:\Windows\System32\DriverStore\FileRepository\`) и с файлами чипа в [linux-firmware](https://git.kernel.org/pub/scm/linux/kernel/git/firmware/linux-firmware.git/tree/) (`mediatek/`, `qca/`), которые разрешено распространять и которые пользователи BlueCaster могут скачать

Отметьте паузы, которые драйвер выдерживает между шагами (по отметкам времени в записи): пока чип перезагружается, он не отвечает.

{: .warning }
Работайте по записям, отчётам опроса и документации производителя. Не копируйте код под GPL и не повторяйте его близко к тексту, например драйверы ядра Linux `btmtk` или `btqca`. BlueCaster распространяется под Apache-2.0 или MIT, и загрузчик, основанный на таком коде, принять не получится.

## Проверка без сборки: скрипты чипа {#chip-scripts}

Прежде чем писать загрузчик, проверьте записанную последовательность на адаптере с помощью **скрипта чипа**. Это текст, по одному запросу в строке, который выполняется вместо стека Bluetooth. Тот, у кого нет адаптера, может написать скрипт и отправить его владельцу адаптера. Результат вернётся в виде отчёта, и новая сборка не нужна.

**Запуск скрипта**: в режиме разработчика откройте **Разработчик > Чип**, выберите адаптер (с WinUSB), введите скрипт или откройте файл и нажмите **Выполнить**. Ответ на каждую строку появится ниже, а **Показать отчёт** откроет `script-<date>_<time>.json` в `logs\probe\` (скрипт входит в отчёт). Из командной строки: `bluecaster-core --cli -u <adapter> --script <file>`.

```text
# один запрос в строке; числа шестнадцатеричные (0x необязателен), кроме wait, timeout= и chunk=
hci 1001                           # команда HCI: код операции, затем байты параметров
hci fc05 ff
bulk fc09 00 01 02                 # то же через канал bulk OUT
usb in vendor device 63 0 0 4      # control IN: тип, получатель, запрос, значение, индекс, длина
usb out vendor device 64 0 0 01    # control OUT: ..., затем байты данных
wait 100                           # миллисекунды
expect e4 02 01 timeout=5000       # событие: его код и первые байты параметров
bootloader off                     # режим загрузчика (включён с самого начала)
upload mediatek/patch.bin fc6f 01 01 chunk=240 ack=event:e4:02,01
upload-bulk patch.bin fc09 01      # то же через канал bulk OUT
```

- `hci` и `bulk` ждут Command Complete или Command Status на команду (2 с) и записывают ответ с любым статусом
- `upload` отправляет файл из папки прошивки командами с этим кодом операции. Каждая команда содержит байты заголовка и до `chunk` байт файла (по умолчанию 240). После каждой команды скрипт ждёт подтверждения: `ack=complete` (по умолчанию: Command Complete или Command Status этого кода операции со статусом 0) или `ack=event:<code>[:<bytes>]`. Статус ошибки прерывает отправку
- Скрипт останавливается на первой строке, которая не выполнилась (нет ответа, ошибка, нет файла), и называет её
- События, которые не относятся ни к одной строке, тоже сохраняются в отчёте

**Безопасность**: без подтверждения выполняются только запросы, которые заведомо ничего не записывают: стандартные чтения HCI (информационные параметры и параметры состояния, Read Local Name, чтения LE), стандартные запросы дескрипторов USB, `wait`, `expect` и `bootloader`. Скрипт с любой другой строкой выполняется только с вашего разрешения (**Выполнить их** под списком таких строк; `--allow-writes` в командной строке). Команды производителя, которые могут записать в память чипа данные, сохраняющиеся после отключения питания, не выполняются никогда, что бы вы ни разрешили (`denied_opcodes` в `app/src/crates/bt-host/src/chips.rs`: пока это BCCMD от CSR). Режим загрузчика включён с самого начала, поэтому при закрытии адаптера после скрипта HCI Reset не отправляется. Прошивка, загруженная в ОЗУ чипа, стирается после переподключения.

## Шаг 4. Напишите загрузчик

Далее пути указаны от корня репозитория. Важны три крейта:

| Крейт (пакет) | Папка | Что там |
|:--|:--|:--|
| `bt-host` | `app/src/crates/bt-host` | Хост Bluetooth: загрузчики, опрос, определение чипа |
| `bluecaster-core` (библиотека) | `app/src/crates/core` | Настройки и адаптеры: какой загрузчик запускается |
| `bluecaster-core-exe` | `app/src/core` | Исполняемый файл службы (`bluecaster-core.exe`): запросы окна, примечания к адаптерам |

В названиях двух последних есть «core»; в `cargo -p` указывайте имена пакетов из таблицы.

Загрузчик — это конечный автомат без собственного ввода-вывода. Он получает события контроллера, результаты своих запросов USB и срабатывания таймера и возвращает **действия**, которые выполняет приложение. Поэтому загрузчик можно тестировать без чипа, а подробности USB и многопоточности в него не попадают.

1. Скопируйте `app/src/crates/bt-host/src/bringup/sample.rs`, полный загрузчик для вымышленного чипа вместе с тестами, в `app/src/crates/bt-host/src/<vendor>.rs` (например, `mediatek.rs`). Добавьте `pub mod <vendor>;` в `app/src/crates/bt-host/src/lib.rs`, в алфавитном порядке среди других модулей
2. Не меняйте имена: тип называется `Loader` (используется как `<vendor>::Loader`), `vendor()` возвращает имя производителя. Оставьте тесты в том же файле, как в образце
3. Замените всё, что в образце помечено «made up», тем, что показали шаги 2 и 3: проверку версии, запрос USB, имя файла, команду загрузки и способ её подтверждения, способ запуска прошивки
4. Перепишите комментарий модуля в начале: что нужно чипу, шаги по порядку и откуда взят каждый факт (ваша запись работы драйвера Windows, документация производителя, отчёты опроса). Не ссылайтесь на исходный код других драйверов как на источник шага

### Интерфейс

Всё находится в `app/src/crates/bt-host/src/bringup.rs`.

| Метод `ChipLoader` | Когда вызывается |
|:--|:--|
| `vendor()` | Для строк журнала («MediaTek») |
| `start()` | Один раз, на открытом адаптере, до инициализации HCI |
| `on_event(event)` | Для каждого события HCI: код, длина, параметры |
| `on_control(result)` | С результатом последнего `UsbControl`: прочитанные байты или причина неудачи |
| `on_timeout()` | Когда срабатывает таймер, заданный последним `Timer` |
| `missing_file_hint(file)` | Для журнала, если загрузчик завершился с `MissingFile`: что и куда положить («x.bin from linux-firmware (mediatek/)») |
| `step()`, `progress()` | После каждой порции действий: имя шага («download») и ход его выполнения (сколько команд отправлено из общего числа). Показываются на экране «Адаптеры», пока адаптер запускается |

После `Done` приложение отбрасывает загрузчик: запоздавший ответ до него уже не доходит.

| `Action` | Что делает |
|:--|:--|
| `Command(bytes)` | Отправляет команду HCI (код операции, длина, параметры) через канал управления; записывается в запись HCI |
| `BulkCommand(bytes)` | Отправляет команду (те же байты, что и для `Command`) через канал bulk OUT: некоторые загрузчики принимают прошивку именно так |
| `UsbControl(request)` | Управляющая передача через канал по умолчанию (регистры производителя). Выполняется сразу, и `on_control` получает результат до следующего действия. Попадает в запись HCI как примечание |
| `Bootloader(on)` | Для чипа, загрузчик которого отвечает через канал bulk IN или которому нельзя отправлять HCI Reset (некоторые от него зависают); см. шаблоны. Чипу с ПЗУ, который нормально отвечает на HCI, это не нужно |
| `Timer(ms)` | Запускает или перезапускает единственный таймер загрузчика |
| `Done(Ok(outcome))` | Готово: далее следует инициализация HCI. `AlreadyRunning`, `Loaded { firmware, detail }`, `Rom` (`Probed` используется только опросом) |
| `Done(Err(error))` | Адаптер нельзя использовать: `MissingFile(name)`, `BadFile { file, why }`, `Command { opcode, status }`, `Timeout(step)`, `Rejected(code)`, `BadVersion`, `UnsupportedVariant(v)`, `Unsupported(why)`, `Host(why)` |

Вспомогательные функции, чтобы загрузчику не приходилось разбирать байты вручную:

- `hci_command(opcode, params)` формирует команду
- `parse_event(event)` возвращает `HciEvent::Complete { opcode, status, ret }` (возвращаемые параметры после статуса), `Status { opcode, status }`, `Vendor(params)` (событие 0xFF) или `Other { code, params }` (любой другой код, в том числе собственный код производителя, например 0xE4)

**Файлы прошивки**: загрузчик получает `FileReader` и запрашивает у него файл по **имени без папки** (`"BT_RAM_CODE_MT7961_1_2_hdr.bin"`). Приложение ищет файл в папке прошивки (`%APPDATA%\BlueCaster\firmware`) и в подпапке производителя внутри неё (`firmware\mediatek\`), как в linux-firmware. Эта подпапка задаётся на шаге 6.

### Шаблоны

Каждый из них есть в образце; уберите то, что вашему чипу не нужно.

- **Одна команда — одно подтверждение**: отправьте команду, запустите таймер и в состоянии ожидания принимайте только подтверждение этого кода операции. Это Command Complete или, если результат команды приходит позже, Command Status со статусом 0. Всё остальное игнорируется, чтобы запоздавший ответ не продвинул загрузчик дальше
- **Подтверждение событием производителя**: некоторые чипы отвечают на каждую часть прошивки собственным событием вместо Command Complete. Ждите только это событие (по его коду и параметрам, по которым его можно опознать). Command Complete и Command Status со статусом 0 на эту команду в этом состоянии игнорируйте, но при статусе ошибки в любом из них завершайте загрузчик. В образце Command Complete и Command Status считаются одним и тем же подтверждением, поэтому в его `on_event` для этого нужен `match` и по состоянию, и по событию
- **Несколько файлов** (патч, затем конфигурация): загрузите и проверьте все файлы, прежде чем отправлять какой-либо из них, отправьте их по порядку и укажите последний в `Loaded { firmware, .. }` (остальные упоминаются в строках журнала)
- **Намеренная пауза** (драйвер ждёт 100 ms перед следующим шагом): добавьте для неё отдельное состояние и отправьте `Timer(100)`. В этом состоянии `on_timeout` отправляет следующий шаг, а не завершает загрузчик с ошибкой. В тестах `SimRun::timeouts` учитывает и такие паузы
- **Команда с двумя ответами** (подтверждение, затем событие производителя, например «прошивка запущена»): два состояния, второе со своим таймером. Так устроены `Launching` и `Starting` в образце. Если событие содержит код результата, при плохом коде загрузчик завершается с `Rejected(code)`
- **Статус ошибки** в Command Complete или Command Status завершает загрузчик с `Command { opcode, status }`
- **Режим загрузчика**: `Bootloader(true)` перед первой командой, ещё до проверки версии. При успехе (`Loaded`, а также `AlreadyRunning`) отправьте `Bootloader(false)` непосредственно перед `Done`, чтобы инициализация HCI прошла как обычно. После неудачи оставьте режим включённым: чип всё ещё в загрузчике. В образце это делает `finish()`
- **Прошивка уже работает**: если версия или регистр показывают, что рабочая прошивка уже запущена, сразу завершайте загрузчик с `AlreadyRunning`. Адаптер хранит прошивку, пока на него подаётся питание, а повторная загрузка может закончиться ошибкой
- **Сначала проверьте файл**: разберите и проверьте весь файл, прежде чем отправлять его части (`BadFile` с причиной). Если файла нет, называйте его точное имя
- **Только ваш чип**: если загрузчик охватывает лишь часть чипов производителя, прежде чем что-либо отправлять, проверьте, что адаптер из их числа (по регистру ИД чипа или по USB ID с помощью `ControlRequest::device_descriptor()`). Если нет, завершайте загрузчик с `Unsupported`
- **Записывайте в журнал** то, что узнаёте от чипа, на уровне `info` (ИД чипа, версия ПЗУ, выбранный файл): именно эти строки попадают в отчёты
- Никогда не записывайте ничего во флеш-память или OTP-память чипа. Читайте файлы только через `FileReader`

## Шаг 5. Проверьте его на имитации контроллера

Тесты используют `app/src/crates/bt-host/src/bringup/sim.rs`. Вы пишете небольшую имитацию чипа (`impl SimController`), которая отвечает на команды и управляющие передачи так же, как настоящий чип в вашей записи. `sim::run(&mut loader, &mut chip)` управляет загрузчиком точно так же, как приложение, включая таймер. Результат (`SimRun`) содержит итог, каждую отправленную команду с её каналом (`commands[i].bulk`), каждую управляющую передачу, режим загрузчика в конце (`bootloader`) и сколько раз срабатывал таймер. `sim::command_complete`, `command_status`, `vendor_event`, `event` (любой код), `opcode` и `params` формируют и читают байты; на команды bulk отвечайте в `bulk_command`.

Как и в образце, охватите как минимум:

- полную загрузку с проверкой отправленных команд (количество, порядок, размеры, канал)
- режим загрузчика в конце каждого случая, если загрузчик его использует
- уже работающую прошивку
- отсутствующий файл и повреждённый файл (из которого ничего не отправлено)
- отклонённую команду (статус ошибки), молчащий контроллер (тайм-аут) и каждое ожидание, которое может истечь по тайм-ауту
- неудачную передачу USB, если загрузчик её использует

Лучшие тестовые данные — байты, скопированные из вашей записи. Запустите тесты так:

```bat
cargo test -p bt-host
```

## Шаг 6. Подключите его к приложению

Ниже перечислены все файлы, которые нужно изменить, — и для производителя, уже указанного как неподдерживаемый (MediaTek, Qualcomm), и для нового. Для нового производителя компилятор сам укажет на выражения `match`, которым нужен его вариант. Всё остальное (а для уже указанного производителя — вообще всё) можно найти только по этому списку.

**Один чип или весь производитель?** Обычно загрузчик охватывает лишь часть чипов производителя (MT7921, но не MT7925). Тогда статус «не поддерживается» снимается только с этих чипов: внесите их VID:PID в `LOADER_CHIPS` в `app/src/crates/bt-host/src/chips.rs` и оставьте производителя в `listed_chips_only()`. В этом случае `chips::chip_supported(vendor, vid, pid)` и `chip_support_tag()` отвечают для каждого адаптера отдельно. От них зависят метка в имени адаптера, его примечание на экране «Адаптеры», доступность там WinUSB и предупреждение «not implemented». Убирайте производителя из `listed_chips_only()` только для загрузчика, который охватывает все его чипы (как у Intel).

{: .note }
Сохраняйте окончания строк каждого файла: в одних исходных файлах используется CRLF, в других LF. Некоторые редакторы и `sed -i` в Git Bash незаметно их меняют, а `cargo fmt` не восстанавливает. Это видно по `git diff --stat`: файл, изменённый в нескольких местах, показан как изменённый целиком. В этом случае перед коммитом верните прежние окончания строк (например, переключателем окончаний строк в строке состояния VS Code).

**Определение** (`app/src/crates/bt-host/src/chips.rs`):

1. `ChipVendor`: новый производитель получает вариант (со строкой документации) и ветвь в `name()`. Для любого производителя обновите комментарий документации перечисления (у каких производителей есть загрузчики) и строку документации варианта («not supported»)
2. Часть чипов: их VID:PID в `LOADER_CHIPS` и тест в модуле загрузчика, проверяющий, что его собственная проверка чипа (ИД чипа, версия) принимает ровно те чипы, что указаны в этих записях. Весь производитель: уберите его из `listed_chips_only()`
3. `vendor_for_usb()`: USB VID производителя. VID, который используют и другие производители, нужно сопоставлять как `VID if pid == PID`, никогда целиком: модули для ноутбуков под VID производителя модуля (AzureWave 0x13D3, Foxconn 0x0489) и общие VID, например pid.codes 0x1209. Каждый указанный здесь VID также заставляет `is_bluetooth_vendor_vid` считать устройства этого производителя адаптерами Bluetooth. VID:PID из таблицы Realtek в BTstack или из `OEM_TABLE` (обе в `resolve_realtek_pid` этого файла) считается Realtek ещё до обращения к `vendor_for_usb`: убедитесь, что вашего нет ни в одной из них
4. `company_name()`: company ID Bluetooth SIG из Read Local Version, если его там ещё нет
5. Тесты: `app/src/crates/bt-host/tests/chips.rs` (VID:PID и метка)

**Открытие адаптера**: устройства класса Bluetooth (класс E0/01/01) открываются без изменений. Если чип в своём ПЗУ сообщает класс производителя (FF), его VID:PID нужно также добавить в `BUILTIN_VENDOR_CLASS` в `app/src/crates/core/src/adapter.rs`; класс показан в строке `usb.interfaces` отчёта опроса.

**Запуск загрузчика**, как у Intel (ищите `intel_loader`):

6. `app/src/crates/bt-host/src/lib.rs`: поле `HostConfig`, как `intel_loader` (со значением по умолчанию в `HostConfig::new`, деструктуризацией в `BtHost::launch` и строкой отладки), и ветвь в `BtHost::launch`, которая устанавливает транспорт и вызывает функцию запуска приложения вместо `setup_hci_and_power_on`, только если это не H4 (`&& !tcp`, как у Intel: контроллер эмулятора не настоящий чип). За один запуск работает только один загрузчик: если установлены флаги двух производителей (оба адаптера на WinUSB), срабатывает первая ветвь. Поэтому при тестировании WinUSB должен быть только у вашего адаптера
7. `app/src/crates/bt-host/src/app.rs`: `start_<vendor>_loader`, как `start_intel_loader` (с `use crate::<vendor>;`), который передаёт загрузчику `read_firmware_file(&dir, "<vendor>", name)` (имя подпапки как в linux-firmware) и вызывает `start_loader`
8. `app/src/crates/core/src/adapter.rs`, `configure()`: установите поле, когда адаптер этого производителя с `chips::chip_supported(a.vendor, a.device.vid, a.device.pid)` находится на WinUSB и не занят (как `config.intel_loader`, с сообщением журнала Intel «in use by another program» для остальных), и добавьте его там в строку отладки `adapter:`. Предупреждение «firmware loading for this chip is not implemented» ниже уже учитывает `chip_supported`
9. `app/src/crates/core/src/service.rs`, `host_config()`: добавьте поле в строку отладки

**Что показывает окно**:

10. `app/src/core/src/state.rs`, `vendor_note()`: ветвь с новым ключом `firmware.vendor_<vendor>`, вынесенная из ветви `MediaTek | Qualcomm`, и её тест. До этой ветви функция возвращает `firmware.vendor_unsupported` для чипов, которые отклоняет `chip_supported`, поэтому у остальных чипов производителя это примечание сохраняется. Экран «Адаптеры» предлагает WinUSB каждому адаптеру, у которого примечание не `firmware.vendor_unsupported`
11. `app/lang/*.json` (все 10 языков, одна и та же строка в каждом): новый ключ, как у Intel («Intel adapter. …»). Если в нём упоминается кнопка или папка, используйте слова соответствующего языка из того же файла (кнопка папки прошивки — `firmware.open_folder`). Весь производитель: уберите его название из `firmware.vendor_unsupported`. Часть чипов: оставьте его там, так как остальные чипы производителя по-прежнему показывают этот текст
12. `app/src/ui/src/lib/links.ts`: страница прошивки производителя (в `LINKS`, `firmwareUrl()` и `vendorFirmwareUrl()`, как папка Intel в linux-firmware), чтобы экран «Адаптеры» показывал, где взять файлы; тесты — в `app/src/ui/src/lib/chips.test.ts`. Экран «Адаптеры» показывает эту страницу только адаптерам, у которых примечание не `firmware.vendor_unsupported`, поэтому для остальных чипов производителя её не будет

**Документация**:

13. Таблица чипов в `docs/setup.md` и `docs/*/setup.md` (все языки): строка, как у Intel, с охваченными чипами, файлами прошивки и тем, куда их класть (папка прошивки: `%APPDATA%\BlueCaster\firmware` или её подпапка `<vendor>`; в более старых строках ещё написано «config folder»). Называйте кнопки окна так, как они записаны в `app/lang/*.json` соответствующего языка (`ui.nav.adapter` для раздела «Адаптеры», `firmware.open_folder` для кнопки, открывающей эту папку). Весь производитель: уберите его из строки «Not supported». Часть чипов: оставьте производителя там и перечислите чипы, которые по-прежнему не поддерживаются. Добавьте производителя в предложение в начале раздела о прошивке («Intel and Broadcom adapters may need firmware files of their own»)
14. [Проверенное оборудование](hardware) (`docs/hardware.md`), когда кто-нибудь проверит загрузчик на деле, и вступление этой страницы (`docs/chip-support.md`, все языки), где перечислены производители без загрузчика (часть чипов: «the other <vendor> chips»)

## Шаг 7. Проверьте на адаптере

Соберите в корне репозитория (`cargo build --release -p bluecaster-core-exe`), закройте установленное приложение (через его значок в области уведомлений) и запустите ядро из командной строки с записью HCI:

```bat
target\release\bluecaster-core.exe --cli -u 0e8d:7961 --scan 5 --hci-capture loader.pklg
```

В журнале виден каждый шаг, а `loader.pklg` открывается в Wireshark со всеми командами, событиями и управляющими передачами по порядку. Отключите адаптер (или выключите компьютер) и попробуйте снова. Загрузка должна работать на холодном чипе и ничего не делать, если прошивка уже запущена.

{: .note }
Если WinUSB назначен нескольким адаптерам, BlueCaster выбирает адаптер Realtek и применяет его настройку чипа, даже с `-u`. Выберите **Не Realtek** в **Адаптеры > Чип Bluetooth** или оставьте WinUSB только у вашего адаптера.

Затем некоторое время передавайте звук на наушники через окно и проверьте, что после **Перезапустить Bluetooth** и после переподключения адаптер снова работает. Пока адаптер запускается, экран **Адаптеры** показывает состояние загрузчика под состоянием Bluetooth («загрузка 42%» или сообщение об ошибке). В режиме разработчика оно остаётся видно и после запуска адаптера, с вашими именами `step()` и итогом.

```bat
pnpm install

```

Затем в корне репозитория:

```bat
cargo fmt --all

```

Если Node.js нет, запустите тесты и clippy только для трёх крейтов выше (`-p bt-host -p bluecaster-core -p bluecaster-core-exe`), а проверку интерфейса оставьте CI. Напишите об этом в pull request. `pwsh ./build.ps1 -Test` запускает всё.

Clippy проверяет и имена: вариант `State` с именем `PatchState` не проходит `enum_variant_names`; назовите его `Patch`. `check_lang.py` может сообщать «long hints left» о подсказках, которые были длинными и до вашего изменения. Исправлять нужно только ошибки и отсутствующие ключи.
